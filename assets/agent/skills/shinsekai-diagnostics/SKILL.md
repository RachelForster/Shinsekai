# Shinsekai 故障排查

先定位失败环节，再提出最小修复。记录「已观察」「可能原因」「验证方法」，证据不足时保持假设，不把猜测写成结论。

## 收集证据

1. 确定版本、操作系统、桌面发行包或源码启动、实际启动命令、首次失败的步骤、最近改变的配置。
2. 优先使用已有诊断工具读取脱敏摘要及相关时间段日志；没有这些工具时，请用户提供错误文本及最少必要的上下文。
3. 不要求 API Key、完整凭据文件或未脱敏的全量日志。用户意外提供秘密时不重复展示，建议移除并视情况轮换。
4. 分清用户使用的环境与工具运行环境。检查进程实际可见的 PATH、Python 或模型配置，不能仅凭另一终端验证成功就宣称问题解决。

## 按失败阶段缩小范围

| 阶段 | 优先核对 |
| --- | --- |
| 源码启动或构建 | 当前目录、Node/pnpm/Rust/Python 是否在该进程可见，依赖是否安装 |
| 模型连接 | 提供商、模型名、基础地址、连接测试结果；401/403、模型不存在、网络超时分别处理 |
| 资源与语音 | 路径、资源是否下载完成、所选形象或语音服务、首条加载错误 |
| 插件加载 | 插件入口、依赖、配置、加载日志与实际启用状态 |
| 助手准备 | 界面准备阶段、模型配置、运行包下载或校验错误 |
| 助手执行 | 任务状态和错误码；排队、等待输入、取消中均不是完成 |

常见恢复提示：`AUTH_REQUIRED` 检查 API 设置；`BACKEND_UNAVAILABLE` 检查准备状态；`SESSION_BACKEND_MISMATCH` 应用当前模型并新建 session；`WORKER_LOST` 保留已知结果，先核对再重新提交。仅在证据吻合时使用这些判断。

## 修复与验证

1. 针对证据最强的原因做最小调整，说明预期变化与验证方式。
2. 使用真实注册的工具执行已授权操作；没有执行能力时给用户明确步骤，不假装已经修改或运行。
3. 优先检查配置和环境，不用删除全部配置、重装应用或跳过校验作为默认解法。
4. 按用户原来失败的路径重新验证。报告实际执行的方法、输出及尚未验证的部分。
5. 写操作结果为未知或任务中断时，先查询当前状态，避免盲目重试造成重复修改。

## 输出

先说明可证实的原因或当前最可能的假设，然后给出修复步骤、验证结果和下一步。把「修复建议」「修改已提交」「原故障已验证消失」分别说清楚。
