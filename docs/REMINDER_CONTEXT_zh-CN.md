# 提醒提示词上下文与角色动作提案

## 本次实现

每次生成角色提醒时，提供以下上下文：

| 字段 | 含义 |
| --- | --- |
| `current_date` | 生成时本机当地日期，格式为 `YYYY-MM-DD` |
| `current_time` | 生成时本机当地时间，包含 UTC 偏移 |
| `due_at` | 本次提醒原定时间，与当前时间分别保留 |
| `previous_reminder_count` | 同一事件此前已确认投递的次数，不含本次 |
| `reminder_number` | 本次是第几次提醒，即此前次数加一 |
| `expression_style` | 每次随机选择的表达方式，如直接提醒、关心、简短问句、轻松打趣或鼓励 |

次数按日程 ID 累计，跨重复周期、角色切换、编辑和应用重启保留。领取租约、失败重试、重复确认、取消和离线漏发不会增加次数。桌面现有流程先确认投递再显示提醒，因此计数表示已提交的投递，不代表用户已经读到、听到或完成事项；确认后进程崩溃也可能未实际显示。

旧数据库会自动补充计数字段，从零开始累计。已有数据没有保存历史次数，因此不推算升级前的投递次数。第一次新提醒的上下文为「此前 0 次，本次第 1 次」。

表达方式只影响措辞，不改变提醒时间、任务、数字或角色性格；仍保留用户配置的生成温度。日期与次数无需每次念出来，也不能据此认定用户忽略了提醒。随机选择可能重复，不能保证每次生成不同的句子。生成失败时仍使用保存的原文。

## 后续可行方案：角色提出动作请求

此部分是方案，尚未实现脚本执行。现有提醒工作流禁用工具，只返回一句对白；目前不存在「点同意执行关机」的闭环。

可以在提醒旁增加请求卡片。例如角色说「已经很晚了，要我帮你关机吗？」，卡片列明「关闭这台电脑」并提供「同意关机」「暂时不要」。请求的内容和执行状态与普通对白分别记录。

建议先实现一个固定的关机动作，再扩展用户配置的脚本：

1. 用户在日程设置中开启允许提出的动作。模型只能选择该日程允许的动作 ID，不能提交命令、脚本正文或任意路径。
2. 宿主把动作 ID 解析为预设动作，生成待确认请求，绑定事件、当前提醒、目标设备和到期时间。卡片由宿主描述实际操作，角色对白仅作引导。
3. 用户明确点击同意后，后端原子地把请求从「待确认」转为「执行中」，调用固定处理器。重复点击或重试不重复执行；拒绝、过期或取消日程后不能再执行。
4. 关机采用可取消的倒计时，并尊重系统对未保存工作的提示。提示倒计时期间允许取消，不能强制关闭应用；执行请求的结果与实际关机完成区分。
5. 自定义脚本由用户预先选定和查看，记录版本或内容摘要、固定参数及工作目录；执行前再次校验，脚本变化需重新确认。Windows 后台进程不弹出无关窗口。

可复用提醒卡片、桌面 IPC、认证 bridge 和日程存储机制；需要新增持久化动作请求、确认接口及受限执行器。普通提醒即使没有动作、用户拒绝或动作失败，也应正常显示。

验证可使用模拟执行器覆盖同意、拒绝、重复点击、过期、日程变更、脚本变更和执行失败，不需要真的关闭开发电脑。
